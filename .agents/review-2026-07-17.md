# Project review — 2026-07-17

Статическое ревью `dddns-updater`. Этот файл — рабочий бэклог: пункты следует
уточнять и закрывать отдельными изменениями с тестами. Исходный код в рамках
ревью не менялся.

## 1. P0 — исправить до использования с рабочими DNS-записями

### 1.1. ✅ Некорректная проверка непубличных IPv4-адресов — выполнено 2026-07-17

Файл: `DnsUpdater/Services/IpAddressExtensions.cs`

- Для диапазона `172.16.0.0/12` отсутствует нижняя граница: условие принимает
  также публичные адреса `172.0.0.0–172.15.255.255`.
- Для benchmark-сети указан `192.18–192.19`, хотя должно быть
  `198.18–198.19`.
- Текущие тесты закрепляют это неверное поведение.

Риск: сервис может не обновить DNS для публичного IP либо принять служебный
адрес за допустимый.

Решение:

1. Выбрана безопасная политика: DNS обновляется только для globally reachable
   IPv4-адреса по реестру IANA IPv4 Special-Purpose Address Space.
2. Проверка перенесена в `IsNotGloballyReachableV4`; исправлены диапазоны
   `172.16.0.0/12` и `198.18.0.0/15`.
3. Добавлены проверки границ частных, служебных, documentation, benchmark,
   loopback, link-local и IPv6-адресов.
4. Проверка: 32/32 фильтрованных тестов `IpAddressExtensionsTests` прошли.

### 1.2. Потеря дополнительных A-записей у DNS-провайдеров

Файлы: `DnsUpdater/Services/DnsProviders/TimewebDnsProvider.cs`,
`DnsUpdater/Services/DnsProviders/BegetDnsProvider.cs`

- Timeweb находит и удаляет только первую A-запись, затем добавляет новую;
  остальные A-записи могут остаться со старым адресом.
- Beget заменяет весь массив A-записей единственной новой записью.

Риск: удаление статических/балансировочных записей или сохранение старых
адресов в DNS.

Задача:

1. Определить контракт: управлять конкретной записью, всеми динамическими
   записями или ровно одной A-записью только после явного подтверждения
   конфигурацией.
2. Реализовать стратегию без затрагивания неуправляемых записей.
3. Добавить unit/contract-тесты для нуля, одной и нескольких A-записей.

### 1.3. Тесты JsonUpdateStorage не проверяют заявленную конкуренцию

Файл: `DnsUpdater.Tests/Services/JsonUpdateStorageTests.cs`

- Локальная функция объявлена как `async void`; `Task.WhenAll` ожидает запуск
  делегатов, но не завершение `Store`/`Query`.
- Используются стандартные `./data/...` пути. Запуск тестов может менять
  пользовательскую историю и создавать backup-файлы.

Задача:

1. Сделать локальную функцию возвращающей `Task`.
2. Использовать уникальный временный каталог на тест и гарантированно удалять
   его в teardown.
3. Отдельно покрыть параллельные Store/Query и ротацию истории.

## 2. P1 — надёжность и наблюдаемость

### 2.1. Автоматический backup может пропустить новое изменение

Файл: `DnsUpdater/Services/IUpdateStorage.cs`

`ShouldBackup` использует `LastOrDefault()` для файлов в фиксированном порядке,
а не самое новое время изменения. Если `settings.json` изменён позже
`updates.json`, условие может решить, что backup не нужен.

Задача: брать максимальное `LastWriteTime`, добавить тест на порядок и на
отсутствующие файлы.

### 2.2. Отсутствует создание рабочих каталогов

Файл: `DnsUpdater/Services/IUpdateStorage.cs`

Запись `updates.json`, создание zip и перечисление backup-файлов предполагают,
что `data/` уже существует.

Задача: создавать родительские каталоги перед записью, валидировать пути и
ограничения `MaxUpdatesPerDomain`/`MaxBackups` при старте.

### 2.3. Healthcheck сообщает успех до завершения работы

Файл: `DnsUpdater/Services/Jobs/UpdateDnsJob.cs`

В начале задачи отправляется `Success`, а при ошибке определения IP или
обработки провайдера не отправляется `Failure`.

Задача: в начале отправлять `Start`, после успешной обработки — `Success`, при
ошибке — `Failure`; заранее определить семантику частичного успеха нескольких
провайдеров.

### 2.4. Timeweb: query и жизненный цикл токена

Файл: `DnsUpdater/Services/DnsProviders/TimewebHttpClient.cs`

- `limit=100` включён в `UriBuilder.Path`, а не `UriBuilder.Query`.
- Bearer token кэшируется бессрочно, хотя ответ API содержит `expires_in`.

Задача: строить query отдельно; хранить время истечения токена, обновлять его
заранее и повторять запрос после отказа авторизации один раз.

### 2.5. Устойчивость внешних HTTP-вызовов

Файлы: реализации в `DnsUpdater/Services/DnsProviders/`,
`DnsUpdater/Services/IpProviders/`

Задача: задать именованные HttpClient с timeout, ограниченными retry/backoff
для transient-ошибок, логированием без секретов и метриками причин сбоев.

## 3. P2 — безопасность, эксплуатация и поддерживаемость

### 3.1. Валидация конфигурации при старте

Пустые или неправильные настройки обнаруживаются только во время запуска job.

Задача: добавить options validation для путей, cron, provider name, доменов и
обязательных полей конкретного провайдера; завершать запуск с понятной ошибкой.

### 3.2. UI для внешней сети

Файл: `DnsUpdater/Views/Home/Index.cshtml`

Страница отображает историю IP и доменов, а также сведения об ОС и runtime без
аутентификации.

Задача: если сервис доступен извне, добавить опциональную аутентификацию и
убрать диагностические сведения из обычного UI.

### 3.3. Время в истории

Файлы: `DnsUpdater/Services/IUpdateStorage.cs`,
`DnsUpdater/Views/Home/Index.cshtml`

В базу записывается `DateTime.Now`, тогда как UI маркирует его как UTC.

Задача: перейти на `DateTimeOffset.UtcNow` и форматировать время в UI явно.

### 3.4. Незавершённые провайдеры

Файлы: `NicRuDnsProvider.cs`, `RegRuDnsProvider.cs`, `Program.cs`

Часть кода провайдеров присутствует, но не зарегистрирована и не выполняет
полноценное обновление записи.

Задача: пометить как experimental и исключить из основного пути либо закончить
реализации вместе с интеграционными/контрактными тестами.

## 4. Сильные стороны проекта

1. Чёткие границы между DNS-провайдерами, источниками IP, storage,
   уведомлениями и healthcheck.
2. Расширяемость через DI, `IDnsProvider`, `IIpProvider` и keyed services.
3. Есть защита от конкурентного запуска Quartz job и синхронизация JSON storage.
4. Пользовательские настройки и секреты вынесены из репозитория.
5. Docker-сборка двухэтапная; CI собирает, публикует и подписывает образы.
6. Базовые unit-тесты уже есть — их можно развить в надёжный регрессионный набор.

## 5. Рекомендуемый порядок работы

1. IPv4-проверка и её тесты.
2. Безопасная стратегия обновления нескольких A-записей.
3. Изоляция и исправление async-тестов storage.
4. Backup, каталоги, UTC и семантика healthcheck.
5. Валидация конфигурации и устойчивые HTTP-клиенты.
6. Защита UI и решение по незавершённым провайдерам.
